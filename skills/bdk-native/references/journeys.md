# Journeys

Step-by-step detail for the two main journeys. The rules in SKILL.md apply to every step.

## First app (new customer)

1. **Explain and ask.** Explain BDK in a few lines. Get current prices (`bdk_estimate`, or https://thebdk.com/agent/pricing.md as data) and show them per platform without assuming a choice. Ask for the published site URL and iOS / Android / Both. Confirm the site belongs to the customer. Propose a project name and get approval.
2. **Connect and find or create the project.** Call `bdk_whoami`. Look for an existing project for this site and ask whether to continue it before creating another.
   - If the customer already has a preview, they can use **Create my app** from that preview at https://thebdk.com/native to carry its settings into the project (or use `bdk_create_project` with `from_preview_id`, see tools.md).
   - Otherwise call `bdk_create_project` with the approved reference label and the published URL. Then set the approved home-screen name with `bdk_configure` field `app_name`. The project name does not set the home-screen name.
   - If `bdk_create_project` returns `project_choice_required`, show the candidates and let the customer choose `create_new` or `use_existing`. Never choose for them.
3. **Offer the preview.** The customer may decline.
   - `bdk_setup_preview` with `intent: "list"` lists previews; `intent: "new"` with `app_link` creates one; `intent: "update"` with `app_link` and `preview_id` replaces a selected preview's link and keeps its name. Ask before replacing a link. Every update needs the `preview_id` the customer picked; never guess from IDs.
   - Send only a published app address, never an editor or builder-share link. The tool checks the link, reuses a preview for the same address, and enforces the 20-preview cap (at the cap, the customer deletes one on the portal).
   - The customer installs BDK Preview from https://thebdk.com/apps#preview. At the portal's Preview view, **Launch** gives them a code or QR. Owner pairing codes work once and expire after one hour; Launch again gives a new one. Tell them: "This code signs in to your account. Only use it on your own phone." Never ask for the code in chat.
   - On iPhone, BDK Preview opens only the signed-in account's own previews.
   - A preview does not prove production push, OAuth, deep links, permissions or store approval.
   - New previews can also be made by pasting the published link on https://thebdk.com, or at https://thebdk.com/preview?new=1 while signed in.
4. **Propose defaults.** Suggest name, icon, colours, permission messages and supported settings as replaceable defaults. Save only approved fields with `bdk_configure`. Use `bdk_upload` only for supported public images; otherwise the customer uploads on the portal. Run the readiness checklist and feature mapping when relevant, with evidence and the disclosure block. Ask which builder they use before giving implementation advice.
5. **Confirm the platform.** Ask iOS / Android / Both, send the answer as `confirm_product` on `bdk_next`, then read `bdk_next` again. If the saved and confirmed values differ, ask again and send the answer through `confirm_product`; don't try to fix it with `bdk_configure`. If the platform is locked, relay the refusal and point to the portal support chat.
6. **Checkout.**
   - Before checkout, explain store enrolment and testing using current store guidance; the customer owns those steps. Suggest starting Apple enrolment early, with no timeline claims.
   - Read `next.commerce`. Don't offer another build purchase when a build is already available, requested or delivered.
   - Get current offers with `bdk_estimate`, explain the purchase terms, and get purchase approval.
   - Call `bdk_checkout` with `action: "start"`, `kind: "build"` and an explicit unique `attempt` for this purchase intent. Reuse the same `attempt` only to retry that same intent. Pass `promotion_code` only if the customer gave one. Keep the `purchase_id`.
   - Convert `quote.total_minor` from minor units and state it in `quote.currency` before relaying your own returned URL unchanged. If there is no `quote`, say the amount is shown on the payment page.
   - Ask the customer to tell you when payment is done, then poll with `action: "poll"` and the `purchase_id`. `status: "paid"` with `fulfilled: false` is not usable yet. An unclear error is not permission to start another purchase: read `bdk_next` and Purchases first.
7. **The portal visit.** Use `next` and its `sitting_brief` for what remains on the portal: visual screen review, credentials and unsupported fields. You can draft store-listing copy for the customer to paste into App Store Connect and Play Console; `bdk_configure` only saves the documented listing-status and account fields. The customer creates the app records named in the portal guide. Accepting terms needs a separate yes for this project (link https://thebdk.com/terms). After credential or screen changes, call `bdk_check` with `run: true` and read the result again after a minute.
8. **Request the build.** Read `bdk_next` again; if `can_request_now` is false, follow its next step first. Explain any holds or failed checks. Only after explicit build approval, call `bdk_build` with `action: "request"`, `build_kind: "build"` and `confirm_build: true`. Relay refusals accurately. Use `bdk_next` for workflow state and `bdk_build` `action: "status"` for delivered history. Delivery is not store submission or approval. Follow the portal's After the Build steps; the customer tests and submits from their own store accounts.

## Existing project

1. Verify access with `bdk_whoami`. List and select a project unless the customer gave a project code; use a given code directly after verifying access.
2. Call `bdk_next`, explain the state and how fresh it is, and ask what the customer wants if they haven't said. Don't repeat first-time setup or push a preview. Change preview settings only when asked. `bdk_projects` is a status snapshot, not a full settings readback; unexposed settings are reviewed on the portal.
3. Do what was asked: explain status, share delivered build links with `bdk_build` `action: "download"`, or propose and apply approved supported changes. Respect holds, active requests and portal-only steps. If the server reports a build request made before the project moved to Purchases, follow that existing status and holds; a missing ledger request is not a reason to request another build.
4. **Rebuild with a banked rebuild.** Check `commerce.can_request_rebuild`, `available_rebuild` and any active request. Read `bdk_next` again; if `can_request_now` is false, follow its next step first. A rebuild builds whatever is saved in Build Settings at the time of the request, so confirm the intended icon, screens, settings or feature changes are saved first. Explain that the request uses one banked rebuild and get explicit consent. Then call `bdk_build` with `action: "request"`, `build_kind: "rebuild"` and `confirm_consumes_rebuild: true`. Never use `free_rebuild` on ledger projects. Keep legacy behaviour only when the server says the project uses legacy commerce.
5. **No banked rebuild.** Explain the extra purchase and get current prices. Use the project's purchased platform; don't send a new `confirm_product`. Get offers with `bdk_estimate`. After purchase approval, call `bdk_checkout` with `kind: "rebuild"`, an explicit unique `attempt` and an optional customer-given `promotion_code`. State the `quote` total before relaying the URL unchanged (or say the amount is on the payment page), then poll by `purchase_id` until `fulfilled: true`. The Purchases tab on the portal is the fallback. Read `bdk_next` again, then get consent to use the rebuild before requesting with `confirm_consumes_rebuild: true`. Buying an extra rebuild does not request it.
6. Adding the other platform after a purchase is not available through the tools (`add_platform_unavailable`). Send the customer to the chat on https://thebdk.com.
